# 产品改进方向

> 版本 1.0 · 2026-11-07
> 对象：Auto-WeLearn 全部产物（CLI / Flutter 桌面 / Android）
> 与 `docs/MOBILE_UX.md` 的分工：那份只讲手机端界面与交互；这份讲**能力与流程**（课程、续跑、后台、凭据、统计、工程化）
> 依据：`app/lib/app_state.dart`、`ui/shell.dart`、`lib/core/runner.dart`、`src/core/**`；本机无 Flutter 工具链，未运行验证

---

## 0. 现状一句话

现在的模型是**「一次登录 = 一门课 = 一条内存队列」**：登录后用 `courses.first` 自动开课（`app_state.dart:198`），队列只在内存里，杀进程即归零。所以产品层面能做的改进，本质是三件事的重构：**选择范围、持久化状态、让它在后台活下去**。

## 2. 方向 A：课程选择与多课程队列

### 2.1 现状

| 事实 | 位置 |
| --- | --- |
| 登录后自动 `loadCourse(courses.first.cid)` | `app_state.dart:198–201` |
| 课程列表含 `cid / name / percent`，**已有进度字段** | `core/models.dart:18–23` |
| 切换课程只在桌面账号菜单里，且仅当 `courses.length > 1` 才显示 | `ui/shell.dart:220–265` |
| 移动端账号菜单只有「退出登录」 | `ui/shell.dart:1188–1212` |
| 队列结构是 `List<Lesson>`，不含课程信息；`_loop` 只处理单课程 | `app_state.dart:302` |
| 本地只持久化 `cookie + settings`，不记当前课程 | `app_state.dart:158–166` |

问题：

1. **默认第一门课不等于用户想跑的那门**。课程顺序由接口返回，用户无法预期；`percent` 已经在数据里，却没用于选择。
2. **多门课要跑完一门手动切一门**，且切换会 `lessons.clear()` 重扫（`loadCourse` 开头），中间没有任何"还剩哪几门"的概念。
3. 手机端**没有切换入口**，等于锁死在第一门课。
4. 同一门课可能有多个 `classid`（不同教学班），现在完全没体现。

### 2.2 目标

**登录后进入「课程选择」，而不是直接开课。** 选择结果成为一次运行的输入。

```
登录成功
  └─ 课程选择页（新）
       课程卡列表：名称 · 进度条 · 待处理数(扫描后) · 上次跑过
       勾选 1–N 门  →  [开始扫描]
       上次的选择默认勾上；只有 1 门时跳过此页（减少一次点击）
  └─ 扫描 → 合并队列 → 主页
```

### 2.3 数据与状态改动

```dart
// 新增：队列项带课程身份，跨课程也能定位
class QueueItem {
  final String cid;
  final String courseName;
  final Lesson lesson;
}

// AppState 新增
Set<String> selectedCids = {};        // 本次要跑的课程
Map<String, CourseScan> scans = {};   // cid -> {units, lessons, scannedAt}
String? lastRunCid;                   // 上次跑的课，用于默认勾选
```

- `_loop` 改为遍历 `List<QueueItem>`；每门课用各自的 `CourseMeta` 传 `runLesson`；
- 跨课程时插一次较长间隔（`intervalMax × 3`）并写日志「切换到《课程名》」；
- `progress` / `remainingEstimate` 按合并队列计算；
- 持久化：`app_state.json` 增加 `selectedCids`、`lastRunCid`，登录后恢复。

### 2.4 界面

| 端 | 形态 |
| --- | --- |
| 手机 | 全屏页：课程卡（56 高）×N，右侧复选框；底部「开始扫描（已选 2 门）」 |
| 桌面 | 左栏顶部课程卡改为可切换的下拉 + 「管理课程…」打开同一页 |

课程卡字段：`课程名`（最多 2 行）、`进度 23%`（细进度条）、`待处理 75 节`（扫描后才有）、`上次运行 10-27`。

### 2.5 验收

- [ ] 登录后有 ≥2 门课时出现选择页；只有 1 门时自动跳过
- [ ] 选择结果持久化，重启 App 后仍记住
- [ ] 两门课合并队列跑完，日志能区分课程，服务端两门都推进
- [ ] 运行中不能改选择（入口禁用并说明「运行中」）

**成本**：约 1.5 天（含 `_loop` 改造与状态持久化）。风险点：`runLesson` 现在依赖单个 `meta`，需要改成按 `cid` 取 `CourseMeta`。

## 3. 方向 B：后台运行（锁屏不被杀）

### 3.1 现状

- `AndroidManifest.xml` 里没有前台服务、没有 `WAKE_LOCK`、没有通知权限；
- 挂机靠 Dart `Timer` + `HttpClient`，屏幕一黑系统会冻结进程；
- 一次运行 12 小时不是不可能的任务量，但现在**手机锁屏就基本结束**。

### 3.2 方案

| 层 | 做法 |
| --- | --- |
| Android | `flutter_foreground_task`（或自写 `ForegroundService`）：常驻通知「正在运行 3/75 · 还剩 3h12m」，`WAKE_LOCK` + `WifiLock` |
| 通知 | 每节开始时更新进度；成功/失败可单独通知（可关） |
| 息屏 | 前台服务 + `PartialWakeLock`；不要用 `WakeLock` 全量，耗电 |
| 省电 | 引导用户把 App 加入「电池优化白名单」；首次开始运行时给一次说明 |
| 断线 | 服务被杀后重启时读 C 方向的持久化状态继续

### 3.3 验收

- [ ] 锁屏 30 分钟，运行继续，通知栏进度在变
- [ ] 切到其他 App 10 分钟，回来队列仍在推进
- [ ] 系统杀进程后重开，弹出「上次运行中断，是否继续」

**成本**：约 1 天，需要新增一个 Flutter 插件（唯一需要加的依赖），并补 Android 权限。

## 4. 方向 C：断点续跑与运行记录

### 4.1 现状

- 本地只存 `cookie + settings`（`app_state.dart:158`）；
- `statuses` / `results` 全在内存，杀进程即丢；
- CLI 版有 `state.json` + `--resume`（`src/core/state/store.ts`），**GUI 没移植**；
- 好处是服务端完成状态会反映在重新扫描的 `lesson.complete` 上，所以"已完成"能找回；坏处是**部分成功、失败、跳过、中断的节全丢**，重跑时无从判断。

### 4.2 方案

1. 新增 `run_state.json`（应用私有目录）：
   ```json
   {"version":1,"cid":"566","startedAt":"...","items":[{"scoid":"...","status":"failed","code":"HTTP_500","at":"..."}]}
   ```
2. 每节结束**原子写**（写 tmp → rename），桌面 CLI 的 `store.ts` 已有实现可照搬；
3. 启动时若发现未完成运行，主页顶部给一条恢复条：「上次运行中断 · 已跑 12 节 · 继续 / 忽略」；
4. `resume` 语义：跳过 `done`，重试 `failed`（每节上限 2 次，与 CLI 一致）。

### 4.3 验收

- [ ] 运行中杀进程，重开有恢复提示，点继续从中断处开始
- [ ] 恢复后不会重复跑已完成的节
- [ ] 状态文件损坏时自动 `.bak` 并继续启动（照搬 CLI 逻辑）

**成本**：约 1 天，主要是把 CLI 的 `state/store.ts` 逻辑移植到 Dart。

## 5. 方向 D：失败恢复

现状：`_loop` 里失败后直接下一节（`app_state.dart:352`），失败行只能等整轮结束重新扫描再跑；`failedCount` 有计数，没有操作。

建议：

1. 运行结束给一张「本次结果」卡：成功 32 / 失败 3 / 跳过 2，失败项可一键「重试这 3 节」；
2. 队列内失败自动重排：整轮跑完后对失败节重跑一轮（上限 1 次），CLI 已有类似逻辑；
3. 详情抽屉里「只跑这一节」（需 `startRun(only: scoid)` 引擎小改）。

**成本**：0.5 天。

## 6. 方向 E：凭据安全

现状（三个问题叠加）：

1. Cookie 明文存 `app_state.json`（`app_state.dart:158`），路径在应用私有目录，但**任何 root/备份/调试都能读**；
2. 登录对话框把 Cookie 明文回显（截图即泄），这次已经泄了一次；
3. 日志和错误信息可能带上 URL 参数或 Cookie 片段。

方案：

| 项 | 做法 |
| --- | --- |
| 存储 | `flutter_secure_storage`（Android Keystore 支持），至少在 Android 侧改加密存储；桌面可退化为 DPAPI/Keychain |
| 回显 | 输入框改 `obscureText` 或只显示摘要；日志过滤器屏蔽 `Cookie`/`ASP.NET`/`acw_tc` |
| 剪贴板 | 读取后 3 秒自动清空剪贴板（`Clipboard.setData('')`） |
| 退出 | 已有，保留；补「清除所有本地数据」入口 |

**成本**：0.5 天（含一个插件依赖）。

## 7. 方向 F：运行前预览（dry-run）

现状：`runLesson` 边跑边解析，解析出 0 题或答案错时，用户是**跑到那一节才知道**；CLI 有 `inspect` 和 `--dry-run`，GUI 没有。

建议：

1. 扫描完成后给「预检」一步：显示每节的题数、题型分布、口语题数、解析失败的小节清单；
2. 红色标出「0 题但非口语」的小节（大概率解析失配），允许手动排除；
3. 桌面端加「只看不跑」（`inspect` 的 GUI 版）。

**成本**：1 天（UI）+ 半天（排除逻辑）。

---

## 8. 方向 G：统计与复盘

现状：只有底栏的 `已完成 · 待处理`，跑完即忘。

建议（P2，先做最小版）：

- 每次运行结束写入 `runs.jsonl`：时间、课程、节数、成功/失败、总耗时；
- 首页底部加一条「近 7 天」：跑了多少节、成功率、平均每节耗时；
- 课程卡显示「预计还需 3 小时 12 分」（现在只有百分比）。

**成本**：1–1.5 天。

## 9. 方向 H：工程化

| 项 | 现状 | 建议 |
| --- | --- | --- |
| CI | 无 `.github/` | GitHub Actions 跑 `npm test` + `tsc`；Flutter 侧跑 `flutter analyze` + `flutter test`（x86_64 runner，能过） |
| 发布 | README 指向 `release/`，但被 gitignore，**无 GitHub Releases** | 用 Actions 构建 exe/apk 并上传 Release，README 改链 |
| 崩溃上报 | 无 | 至少 `FlutterError.onError` 写本地日志文件，设置页可导出 |
| 版本检查 | 无 | 启动比对 GitHub 最新 release，提示更新（可选） |
| 秘密扫描 | 靠自觉 | pre-commit 加 gitleaks，防 Cookie 再进仓库 |

**成本**：1 天，收益长期。

## 10. 方向 I：合规与限速边界（写进产品本身）

这不是"规避风控"，是让工具不因为自己的行为把账号搞挂：

1. **严格串行**：并发只是把风险集中，收益有限；现在的 `concurrency` 参数建议默认隐藏；
2. **夜间/异常时段限速**：凌晨 3 点连续 300 节比白天更可疑；
3. **单账号提示**：明确写出「不建议多账号/多设备同时跑」；
4. **免责声明落到运行前**：第一次点「开始运行」时弹一次确认，而不是只躺在 README；
5. **不做**：UA 轮换、代理池、设备指纹伪造——与现有 README 的承诺一致，别破例。

**成本**：0.5 天。
